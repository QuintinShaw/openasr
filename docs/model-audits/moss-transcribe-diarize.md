## 1. Graph & scheduling

| Item | Status | Justification / evidence (+ unlock condition if not Supported) |
| --- | --- | --- |
| Graph reuse / persistent session (no per-request graph rebuild) | Supported | Intra-request: one checked-out `MossEncoderRuntime` is reused across every 30s audio chunk. The CPU lane keeps the original scalar adaptor as the exact numerical oracle and retains its separately admitted f32 weights in that actor; accelerated lanes keep native GGUF adaptor handles beside the encoder's mmap-backed handles and append the adaptor to each encoder graph. The Qwen3 decode graph is reused across decode steps on the Metal/single-GPU lane via `run_prefill_auto_last_hidden`/`run_step_auto` (`llm_decoder.rs`); CPU rebuilds the forward graph per step by design of the shared qwen executor. **Cross-request:** finite encoder and decoder `AdmittedPinnedRuntimeActorCheckoutPool`s keep runtimes on dedicated owner threads and reuse them through the same executor (`resident_runtime_cache_hits_on_a_second_transcribe_call_for_the_same_pack`). This supersedes PR #206's historical thread-local `BoundedRuntimeCache`. |
| Op fusion opportunities reviewed (norm+matmul, QKV, rope, ...) | Supported | Encoder blocks use the shared `nn::encoder::transformer_layer` primitive. Decoder reuses qwen's whole-decoder graph, fused QKV projection load, and fused logits head. The adaptor deliberately has two execution paths: CPU preserves the original scalar MLP+LayerNorm reduction order as the exact numerical oracle; Metal/GPU appends time merge, both matmuls, SiLU, and LayerNorm to the encoder ggml graph, binding native GGUF tensors through the already-open encoder weight context. The accelerated path removes the encoder-output readback/re-upload boundary and the host adaptor matmul without changing the CPU reference. |
| Batching / serve-batch path | Deferred | No moss consumer of the shared serve-batch engine; each `execute()` still runs exactly one utterance. Shared serve-batch **policy** is no longer env-gated (PR #215: width/queue from `--max-native-sessions-per-model`, typed 429/503, content identity) and qwen/cohere already consume it -- moss has not wired a decoder runtime into that path. Unlock: implement a moss serve-batch decoder runtime on the #215 policy (same pillar-2 follow-up as firered-aed/firered2-llm). |
| Encode-decode pipelining | Not applicable | Single-shot per utterance: the executor processes independent fixed 30s chunks through one backend-specific encoder runtime. CPU reads back each valid encoder prefix and applies the exact scalar adaptor; accelerated lanes time-merge and adapt the valid prefix inside the encoder graph, returning only final adaptor rows. The executor concatenates those per-chunk adaptor rows, builds one ChatML+audio-span prompt, then decodes. The architecture still needs the full audio up front to place globally continuous numeric time-anchor markers, so there is no encoder chunk stream to overlap with decode. |
| Arena / gallocr reuse across steps (no per-step allocator churn) | Supported | Encoder small tensors (conv stem, 1D norm/bias, fixed positional embedding, final LayerNorm) live in a WEIGHTS-usage static-tensor arena uploaded once per `encode_and_adapt()`; per-chunk mel and the all-zero mask remain graph inputs. FullDevice uses the direct accelerator allocator, while CPU may retain scheduler gallocr. Accelerated lanes bind adaptor tensors from the resident loaded context rather than uploading host copies. The CPU actor retains the separately admitted scalar-oracle adaptor weights. Decoder KV lives in the preallocated per-utterance `Qwen3AsrLayerKvCacheState` arena; CPU rebuilds per token by design of the shared executor. |

Verdicts that apply to this family, so future work does not re-run dead

verdict 2026-07-14); qwen speculative decode (acceptance alpha ~= 0.05, judged

| Dead end | Verdict / evidence | Date |

| Conflating `max_position_embeddings` with the KV-cache working-set size | Dead: the checkpoint's `text_config.max_position_embeddings` is 131072 (the RoPE context ceiling), but a decode allocates two KV copies across the full span, so feeding it straight through reserves ~42 GiB worst case -- 28 GiB host f32 copy (the old "~30 GB" figure counted this copy alone) + 14 GiB resident f16 copy (Metal physically wires the resident copy -> exhausts a 16GB machine many times over). Capped at a pragmatic 8192 ASR context (mirrors qwen3-asr's audio-encoder value), dropping the worst-case reservation to 2.625 GiB across both copies (`runtime_contract.rs:41-92`, the byte arithmetic pinned by `moss_transcribe_diarize::capacity`'s regression anchors).
